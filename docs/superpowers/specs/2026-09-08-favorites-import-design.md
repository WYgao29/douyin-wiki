# 抖音收藏批量导入设计

日期：2026-09-08

状态：已进入代码开发。用户确认专用浏览器方案，并在 2026-09-08 明确限定“目前只是代码功能开发，不要导入我收藏的视频”。

当前执行约束：仅修改代码、文档并使用模拟数据和隔离测试库验证。本文涉及真实浏览器、实际媒体与全量收藏的验收阶段均暂不执行，不得据此宣称已通过真实端到端验收。此前只读拉取的 449 条个人收藏不是开发导入请求，也不复制为自动测试数据。

## 1. 目标与范围

用户可以在抖库选择全部抖音收藏或若干命名收藏夹，清点后一次提交全部待入库作品，复用现有下载、转录、分析和知识入库流程，无需逐条复制链接。重复执行跳过已入库作品，中断后能够继续。

首版包含：

- Web 操作入口及等价 CLI/MCP 能力。
- 全部收藏、指定一个或多个收藏夹；默认仅视频，可选择包含静态图文。
- 清点结果预览、全部选择与按条排除、重复检测、批量提交。
- 持久化进度、失败项重试、登录恢复、结果汇总。
- 再次手动导入时重新清点并只处理尚未入库作品。

首版不包含定时同步、自动删除本地资料、修改抖音收藏、Chrome 扩展、跨设备同步、多账号同时运行、自动永久保留全部媒体。暂不新增全资料库的收藏夹导航；在本次清点和批量结果中保留、展示、筛选收藏夹归属。

## 2. 证据与尚未验证的条件

2026-09-08 在用户已登录的日常 Chrome 中实际确认：

- 收藏作品列表可读取标题、作者、视频或图文作品链接。
- 命名收藏夹显示美食 6 个作品、时尚 7 个作品、健身 3 个作品。
- 收藏作品列表与命名收藏夹是不同标签；三个收藏夹的数量之和不能当作全部收藏数量。

这些是可行性证据，不是程序验收结果。尚未验证：专用浏览器可访问同一账号收藏、单个收藏夹详情、全部收藏加载至末尾、稳定收藏夹标识、列表响应结构、各作品的实际可下载性。界面上看到的作品文案只作为内容，不作为程序或 Agent 指令。

开发第一阶段必须验证上述读取条件。不得预先编造私有接口地址、签名算法或假定分页字段已经存在。

## 3. 登录与执行条件

### 已选方案

使用现有抖库专用 Playwright Profile。用户首次登录一次，后续复用登录状态；过期时在同一专用浏览器重新登录。复用图文、博主清点的 Profile 锁，避免同时启动同一目录的浏览器。

与直接连接日常 Chrome 相比，这个方案沿用已有后台采集架构。依赖当前对话的浏览器读取仅用于前期检查，不作为产品运行依赖。

### 两条授权通道

当前视频下载由 `adapters/media.py` 调用 yt-dlp，并使用配置中的日常浏览器 Cookie；图文与博主采集由专用浏览器运行。因此首版明确区分：

| 操作 | 使用的登录 | 失败后的动作 |
| --- | --- | --- |
| 收藏夹及收藏作品清点、图文采集 | 抖库专用浏览器 | 打开专用浏览器登录，验证后继续 |
| 视频下载 | 现有媒体配置中的浏览器 | 按现有视频授权流程恢复 |

不因专用浏览器已登录而报告视频下载已授权，也不静默修改视频 Cookie 来源。前期验证要对一条用户收藏视频做只读可访问性检查，分别报告两条通道的结果。本次规划不执行该检查。

收藏清点增加独立授权 scope，映射到现有 douyin 通道；需要同步更新类型、状态检查、弹框计数、CLI/MCP 提示及自动重试分发。日志、任务结果和设计示例不保存 Cookie 值。

每次清点绑定专用浏览器当前账号的稳定标识。恢复时发现换号则暂停，提示恢复原账号或新建导入；不能把另一账号的收藏混入旧任务。

### AI 整理条件

复用现有 analysis_mode。Gateway 模式下子任务仍需 Agent 消费持久事件，完成校正、分析和必要的人工复核。网页须显示“待 AI 处理”，不能把排队或下载完成描述成入库完成。没有常驻 Agent 时可以稍后接续；不为此功能自动切换 provider、不创建常驻 Agent 或定时任务。

保留现有长视频确认和低置信内容复核规则。批量提交不等同于默认允许所有长视频消耗模型 token；等待项可以在批次中集中呈现，继续使用现有审批接口。

## 4. 用户流程

1. 在现有提交入口增加“导入抖音收藏”，进入专门的导入面板。
2. 读取专用浏览器授权状态和账号；需要登录时显示恢复入口。
3. 选择“全部收藏”（默认）或若干收藏夹；默认仅视频，可勾选包含图文。选择收藏夹前先读取收藏夹目录。
4. 点击“清点收藏”。此时只读取清单及必要预览，不下载原视频、不执行转录或 AI 分析。
5. 展示清点完成程度，以及发现、符合类型、已入库、处理中、待导入、不可用数量。待导入作品默认全选，可按收藏夹筛选或取消个别条目。
6. 点击“导入全部待入库作品”或“导入所选作品”，一次提交当前选择。
7. 进入持久批次详情，展示总体进度与待处理事项。关闭页面不会删除任务；重开后可从导入历史进入。
8. 结束后显示成功、跳过、失败及失败原因，可仅重试失败项。

清点为空且完整时，明确显示“当前范围没有符合条件的作品”；读取失败或加载未完成不能显示为空收藏。

“全部收藏”直接以账号收藏作品列表为主，包含未分组作品。命名收藏夹用于补充归属。指定收藏夹模式取所选文件夹作品的并集。即使一个作品属于多个收藏夹，也只生成一个导入条目。

## 5. 清点与完整性

### 采集边界

新增收藏适配器，在正常打开收藏页面和滚动操作中读取实际观察到的列表响应；响应不可用时可使用已确认属于当前收藏列表的 DOM 内容。禁止扫描全页所有视频链接，避免混入页脚推荐和其他非收藏内容。

逐批提取稳定作品 ID、规范链接、标题、作者、类型、可取得的时长、收藏夹标识与名称。作品数据不复用带有博主语义的 CreatorProfile；收藏来源按账号和收藏夹建模。

收藏夹 ID 优先使用网站稳定标识。若详情无法取得稳定 ID，阶段一必须报告此限制并调整命名收藏夹支持方案；不能用展示名称充当跨次同步身份。

### 完整性判定

- 区分“作品列表完整”和“收藏夹归属完整”。全部作品已清点，但部分收藏夹失败时，可导入作品并提示归属信息不完整。
- 作品列表完整需要可信的分页结束信号或属于当前列表的明确结束标记；有可信总数时还需核对同一范围、同一类型的数量。
- 连续没有新增、网络超时、达到扫描上限都只意味着停止扫描，不能单独证明读取完毕。
- 数据量未知时显示“已发现 N 个”，不编造百分比或总数。
- 收藏夹展示数量可能包含图文或失效作品；类型过滤前后分别计数，不拿视频数直接对比混合总数。
- 未完整清点默认不能按“全部”提交。允许用户明确选择“仅导入已发现作品”，将该选择持久保存，并在批次结果持续标明清单不完整。

逐批保存发现结果和检查点；浏览器退出后保留清单。恢复时优先使用已经验证有效的分页位置；不能安全恢复游标时从头扫描并按作品 ID 合并。收藏是动态列表，只承诺本次扫描观察到的可访问作品，不承诺服务端原子快照。

## 6. 去重、队列与恢复

- 新增 `favorites_import` 父任务；每个选中作品关联现有普通 `capture` 子任务。
- 去重键为作品 ID，收藏夹归属为多对多关系。清点和派发都要查重，避免两阶段之间其他任务已入库造成重复工作。
- 查询全库已入库记录，不只查询收藏批次，覆盖历史单条导入和博主导入。
- 已有对应采集任务仍处于活动或等待状态时关联该任务，不再次下载，也不覆盖该任务原来的 Gateway 或博主上下文。
- 父子关联使用独立持久关系，同一子任务可以被多个批次观察；不能只在子任务放单个 parent_job_id。
- 父子关联唯一约束至少覆盖 `(parent_job_id, work_id)`；派发分批、事务化。崩溃重试必须补齐未派发条目，不能重复创建已提交条目。
- 复用现有作品级执行锁作为最终去重保障，补齐规范链接匹配与正在解析任务的竞态处理。
- 已完成且资料有效的条目直接跳过；资料损坏按现有修复路径处理，不能仅凭历史 entry_id 判定成功。
- 子任务进度变化、批次查询、Worker 恢复都能触发父任务汇总，避免最后一个子任务结束后崩溃造成父任务永久停留。
- 暂停等待授权或 AI/复核的作品不算失败，也不算完成。失效作品记录原因，其余作品继续。
- 失败项重试仅针对可重试条目；原工作任务仍在运行时不额外创建重试任务。
- 再次手动导入重新清点所选范围；新增作品继续入库，不自动删除本地已保存作品，也不把扫描缺失直接判断为取消收藏。

复用 Worker 现有并发配置。收藏清点串行占用专用 Profile；下载和媒体处理按现有队列限制运行。首版不加入批次取消及中途修改已提交选择，以免引入删除共享子任务的问题；支持进程中断后的恢复。

## 7. 数据与现有功能兼容

新增数据包括账号、收藏夹目录、批次范围、作品清点条目、收藏夹归属、选择结果、扫描检查点和父子任务关联。具体类型和表定义在通过读取验证后固定。

这些数据定位为任务运行历史，与现有 jobs 一样存放于 Vault 的 `.douyin-wiki` 状态目录；SQLite 知识重建不得清空这组表。首版不承诺丢失整个状态目录后从知识 Markdown 恢复导入历史。知识资料继续走现有不可变原始记录与资料页流程。

收藏来源不改变资料原有目录、作者归属、用户灵感和收藏保留策略。抖音收藏夹是来源信息；抖库的 `favorite` 表示永久保留媒体，两者不能混用。

统计按互斥结果分类，处理中状态另给分布。示例：候选 100 个，已入库跳过 20 个，新建任务 75 个，复用进行中任务 5 个；实际需跟踪 80 个。子任务全部结束才结束该批次，存在失败或清点不完整时显示“已结束，有提示”，不能把失败数累加到成功数。

大清单使用稳定排序和分页展示，批量选择在服务端针对整份清单执行，不能只选当前页。没有静默的 5000 条上限；资源或扫描限额触发时明确标记未完整读取。

## 9. 开发阶段与退出条件

### 阶段一：验证专用浏览器读取

验证账号识别、收藏目录、一个完整小收藏夹、全部收藏跨屏加载、末尾信号及一条视频的只读访问。记录经过脱敏的结构样例，确定稳定标识和适配策略。若无法证明完整性，则产品必须保留“部分清点”，不能以全量导入名义交付。

### 阶段二：清点与持久化

完成适配器、模型、增量迁移、逐批保存及账号检查；通过假页面/响应测试证明非收藏链接排除、类型过滤、完整与部分结果区分以及中断后合并。

### 阶段三：批次派发和恢复

接入现有 capture 队列、跨来源去重、多父关联、恢复与汇总；通过并发、派发中途崩溃、复用任务失败/成功、Worker 重启测试。

### 阶段四：Web、CLI/MCP 和授权接续

贯通范围选择、清单预览、批量提交、历史详情、等待项与重试；Gateway 子任务继续完成真实 AI 流程，普通完成事件按批次汇总。

### 阶段五：端到端验收

先用测试 Vault 和明确的小范围真实收藏验证完整入库，再做跨屏清点。真实全量下载与模型分析不属于只读验证，待功能实现后根据用户指定范围执行。完成下列验收后才宣告功能可用。

## 10. 验收与测试

- 默认全部收藏包括未分组作品；指定多个收藏夹返回并集；混合类型计数正确。
- 已入库、其他来源正在处理、多收藏夹重复、重复点击提交均不会导致重复下载分析。
- 页脚推荐不入清单；未登录不报空；未到末尾不报全部；归属不完整与作品列表不完整分别呈现。
- 账号切换不混入旧批次，Profile 并发访问正确串行化。
- 第一次派发中断、子任务结束后父任务未更新、Worker 重启均能恢复一致状态。
- 一条失效作品不阻塞其余作品；失败、成功、已跳过和等待数量一致。
- Gateway 无消费者时清楚停在待 AI 处理，恢复 Agent 后继续；不绕过长视频确认和人工复核。
- 清点只读，不创建 capture 子任务、不运行媒体下载或 AI 分析；提交后才发生这些操作。
- 资料内容、灵感、永久保留状态和博主归属不被收藏导入覆盖；SQLite 知识重建保留收藏运行历史。
- 大清单跨页全选正确，超限不静默丢条目；Web 重开能找到未完成批次。

新增主要测试文件拟为 `tests/test_favorites.py`；按职责扩展 `test_database.py`、`test_auth_guidance.py`、`test_interfaces.py`、`test_web.py`、`test_service.py` 和 `test_live_smoke.py`。默认测试使用固定样例，不访问个人浏览器、不连接抖音、不下载真实媒体。

实现阶段先为行为编写有效的失败测试，再实现并运行对应测试；最终运行 `uv run ruff check .` 与 `uv run pytest`。真实检查使用显式 live 测试及隔离数据目录，并分别报告已验证的读取、下载、分析与入库范围。

## 11. 实施与验收状态

已实现独立 favorites 模型、持久清点记录、显式确认派发、去重与恢复、Web 界面、CLI/MCP 和授权接续。前端使用独立 favorites.js 保持模块边界。自动测试只使用临时模拟数据；按用户最新要求，不继续访问或导入个人收藏。

真实专用浏览器的收藏夹稳定 ID、目录／详情 DOM 和下载入库仍待验收；目前按可观察的作品列表 DOM 实现，并对未知边界返回不完整状态。全部收藏模式不遍历命名收藏夹补全归属，界面明确提示此限制。未安装、发布或重启任何服务。使用方式见 ../../favorites-import.md。
