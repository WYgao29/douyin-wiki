# 长视频导入问题与修改方案

## 范围与当前状态

- 样本：作品 `7686768044248452390`，约 26 分 50 秒；任务 `89ddff78fbb540668307396391232334`。
- 采集结果：859 段 ASR 字幕、60 条 OCR 画面记录、78 条人工复核项。
- 最终状态：`completed_with_warnings`；分析中 6 条无法核实的证据或内容被移除。下载与授权在本次导入中正常。
- 下述已有代码修复仍在工作区，尚未提交。此方案不把独立的 ASR/OCR 模型替换实验当作本次导入故障。

## 修改顺序

### P0：输入预算和可恢复性

1. 在 `adapters/llm.py` 以当前模型 tokenizer 计算完整请求 token（系统提示、JSON、元数据及输出预留量）。以实际预算切分字幕与 OCR；80 段只作为额外上限。模型 tokenizer 不可用时采用保守估算，并在超长 400 后自动缩小批次。
2. 对 `finish_reason=length` 单独处理：保留错误类别；只对可拆分的校正/分析批次自动二分重试。汇总请求改为分层合并，避免把所有批次结果一次送入。不能靠重复同一请求碰运气。
3. 为每批校正、分析和每层汇总保存检查点，附来源内容、模型、提示版本的指纹。Worker 中断或模型短暂故障后仅重做未完成批次；源数据或提示变化时失效旧检查点。

**验收：**用本样本和一个人为压低上下文/输出上限的测试环境验证：无超限请求；输出截断可恢复；中断后已完成批次不重新调用模型；最终证据校验仍开启。

### P0：进度与证据质量

4. 在 `service.py` 和 Web 任务接口中记录 `phase`、`completed_chunks`、`total_chunks`、最近一次模型响应时间；进度从 70% 随批次单调前进，汇总与证据校验各有独立状态。超时或长期没有新响应时展示具体等待点。
5. 汇总时要求证据的引文和定位信息直接继承原始分批结果，并在入库前逐条核验。失败项可用对应时间窗口的原始字幕/OCR做一次定向修复；仍无法核实时删除该证据及失去证据支撑的内容。结果中列出每条被删内容、原因和原位置，保留现有严格校验。

**验收：**Web 可看到批次计数和最后活动时间；构造错误时间戳、虚构引文时不会写入伪证据；警告能定位被删除的具体项目。

### P1：减少无效复核与 OCR 噪声

6. 复核项按字幕段归并，并在入库前过滤：空建议、与原文相同的建议、已应用的更正、重复问题。仅把仍有多个可信读法或重要专有名词无法核实的项目交给用户；保留原文与建议的可追溯记录，不自动接受真正不确定的内容。
7. 原始 OCR 完整保存；发送模型前对相邻抽帧的重复文字做规范化去重，保留最早/最清晰的时间戳映射。仍只给每批字幕附近的 OCR，并设独立 token 预算。

**验收：**用这条视频的 78 条历史复核项回放，报告过滤前后数量和每条理由；重复画面不会重复占用提示词，但原始 OCR 和证据定位不丢失。

### P2：运行保障

8. 对 oMLX 连接失败、502、超时、上下文超限、输出截断分别记录错误码和可操作提示。瞬时 5xx 可有限退避重试；永久 400 不盲目重试。Web 显示模型健康状态、最近错误和本次请求的输入/输出 token 数。
9. 跑完整单测与 lint，再对真实长视频做一次端到端复验；记录耗时、模型调用次数、重试次数、复核数量、证据剔除数和最终条目状态。通过后再提交代码。

## 实施边界

当前 65,536-token 上下文窗口无需因这次事故调大。最初的 127,424-token 请求源于程序一次提交过多内容；8,192-token 输出截断是另一类限制。ASR/OCR 模型替换属于独立的质量与性能评估，不是修复这两种超限的前置条件。

## 2026-09-27 实施复验记录

- 调用层已加入模型 tokenizer 输入预算、保守估算回退、输出截断拆批、分层汇总和按请求指纹保存的检查点。任务进度保存模型响应时间、调用与重试次数和 token 用量。当前本机配置 `max_output_tokens=8192` 时，分析每批最多 40 段。
- 用本视频已保存的 859 段校正字幕与 60 条 OCR 做预算回放：22 批，最多 40 段，估算每批最高 6,162 输入 tokens；60 条 OCR 均进入对应时间窗。各时间窗重复 OCR 共 51,809 字符，逐行去重后输入 46,005 字符；原始采集记录不变。
- 旧 80 段策略的真实 oMLX 复验中，第 6 批到达 8,192 输出 tokens，服务日志显示 `finish_reason=length`。因此增加输出预算对批次数量的约束，并识别服务端的 JSON 截断错误。
- 78 条历史人工复核回放后，18 条仍需复核；48 条单一建议未说明关键歧义、11 条建议与原文相同、1 条没有可操作建议。逐项理由保存在 Vault 的 `.douyin-wiki/reports/review-replay-7686768044248452390.json`，原任务复核记录未修改。
- 使用原任务已保存的校正字幕与 OCR 做完整分析隔离复验，不覆盖现有知识条目。22 个分析批次和 13 次分层汇总均完成；其中两批因结构校验各重试一次。oMLX 日志记录 37 次 HTTP 生成请求（35 次成功结果、2 次重试），累计输入 187,592 tokens、输出 88,721 tokens，没有 `finish_reason=length`。模型生成阶段约 44 分钟；中途修复空引文崩溃后，已完成的检查点被直接复用。
- 最初的纯模型分层汇总只留下 2 章、4 个通过核验的知识原子，丢失了视频后半段。现改为保留分段分析中的时间轴与知识原子，模型汇总仅提供整体概览。最终严格校验后有 11 章、80 个知识原子，时间轴从 0 延续到 1,609,480 ms；31 项无法核实的内容被剔除（8 条章节引文、23 个知识原子）。视频条目误带 `image_index` 与推断类型标记不一致时，先做确定性字段修复再校验。
- 逐项剔除原因保存在 Vault 的 `.douyin-wiki/reports/analysis-replay-7686768044248452390.json`。
- 完整测试为 `347 passed, 1 skipped`；Ruff、`node --check`、`git diff --check` 均通过。此次复验复用了原任务的下载、ASR 和 OCR 结果，没有重建或覆盖任务、知识条目；生产任务在下一次导入时才会产生新的进度及证据审计记录。
